# PriorSeal 独立商业化就绪度（2026-10-20）

本文只说明 PriorSeal 作为独立产品的商业化就绪度；它不以 Insight
接入为前提。Insight 可以作为独立的决策/风险输入产品销售，也可以与
PriorSeal 组合，但两者保持独立的信任根、验证步骤和商业范围。

## 结论

PriorSeal 已具备以**受限自动化的付费设计伙伴试点**形式独立销售和交付
的核心产品能力，也可将 Insight 的决策/风险输入与 PriorSeal 的授权和
证据交付组合销售。它尚未处于可对不特定客户开放自助付费出口的状态。

这里要严格区分技术配置与商业上线：能力接口中 `x402` 或 agent credit 的
`configured` 状态、以及公开的参考价格，只说明部署已载入相应代码或配置；
它们不证明客户已购买、款项可结算，或服务、退款与支持承诺已经生效。
2026-10-18 的零付款检查确认候选 `https://x402.org/facilitator` 未报告
Base 主网 `eip155:8453` 的 `exact` 支持。在有一份带日期的 `ready: true`
零付款检查结果，并完成另行授权的限额付费演练之前，不得宣布自助付款已经上线。

## 现在可以销售什么

现在可以销售的是一个范围明确的 PriorSeal 独立设计伙伴包，而不是泛化的
“自动执行”承诺：

1. 选择一个受限自动化资金操作或链上执行路径。
2. 将授权边界、有效期、允许的执行者、资产/金额/调用约束和证据消费者写入
   试点范围。
3. 交付可复核的授权、执行观察、合规结果和 Evidence Pack。
4. 由客户或其审计方使用独立的 issuer key 信任锚验证证据。

对于 Solana 客户，还可以销售一个 Jupiter ExactIn 受限交换的 Insight +
PriorSeal 设计伙伴试点：Insight 提供可审阅的决策输入，PriorSeal 将允许的
输入/输出 mint、最大输入、滑点、时限、签名者和证据消费者绑定到一次准备、
授权、提交和观察流程。它不承诺报价、成交、收益或资产安全。

这可以按固定范围的付费试点、实施费或企业服务合同收费。PriorSeal 不持有
客户钱包私钥、不替客户广播交易，也不承诺交易的经济安全、盈利性或业务结果。

Jupiter 试点可从[本地试点简报页](https://priorseal.xyz/jupiter/pilot-intake)
开始：该页面只在浏览器内生成非敏感范围简报，不上传、存储或分析填写内容。
公开 GitHub Issue 仅用于已脱敏的开发协作；私密商业线索、合同和资金 GO 必须在
双方同意的私有渠道中处理，不能由该页面或代码擅自收集。

## 目标商业模式：Agent 的按调用授权与证据层

PriorSeal 的目标不是向 Agent 出售无限制的交易能力，而是让 Agent 为明确的
授权和可验证证据按调用使用服务。完整角色分工为：

1. **服务付款方**为 PriorSeal 的 API 使用付费；在未来的自助形态中可采用
   x402 或经审阅的预付费使用额度。
2. **授权人**用自己的钱包或组织控制的账户，对一笔受限、限时、单次使用的
   意图签名。
3. **执行者**在客户自己的执行环境中提交交易；PriorSeal 不接管其私钥或资金。
4. **证据消费者**独立验证下载的 receipt 或 Evidence Pack。

付款不构成对被观察交易的授权。即使付款和执行发生在同一条链，二者也必须在
证据和产品叙述中保持分离。当前 x402 实现只保护只读 receipt-bundle 导出；它
不是创建授权、广播交易或给 Agent 自动授予行动权限的机制。

因此，当前可销售的设计伙伴包按受限操作路径与服务范围定价；未来的自助按调用
模式需要先完成生产支付门槛，再为写入型 API 设计独立、可对账的计量和预付费
机制。不得把该未来能力描述为已上线。

## 尚未完成：公开自助付费上线前的门槛

以下是生产商业化的必做项，不应以 staging 成功替代：

1. 选择并审批实际支持首个主网 payment rail 的 facilitator、生产 payee、
   价格、facilitator 条款、退款/争议负责人和客户支持流程。
2. 对生产 D1/存储完成 x402 ledger migration 与健康检查，配置生产 issuer、
   主网 RPC、facilitator secrets 和最小化的只读付费路由。
3. 按 [x402 production Go/No-Go](../runbooks/x402-production-go-no-go.md)
   运行零支付就绪检查；该检查通过前不得宣布可购买。
4. 获取一次单独的、限定钱包/路由/网络/最高金额的主网结算授权，再进行一次
   可对账的付费演练。不得自动重试未知结算。
5. 将实际客户合同、数据保留期、支持响应、退款/争议处理和证据交付责任与
   试点范围对应；这些是商业运营决策，不应由代码或 staging 记录擅自推断。

若某个部署在这些门槛完成前已经暴露 x402 或 credit 配置，必须将它视为
技术配置异常而不是商业上线证明：停止对外宣称可自助购买，并按变更控制
审查、修正或回滚该配置。不要因为接口出现价格就向客户发出不可结算的付款
挑战。

## 下一步决策

若目标是尽快验证独立商业价值，下一步不是扩展更多链或更多支付 rail，而是
选择一个首个付费设计伙伴的受限操作路径，并完成其试点范围、成功标准、证据
消费者和收费方式。若目标是自助售卖证据 bundle，则先执行生产 Go/No-Go，
不要直接把 staging 测试配置复制到生产环境。
