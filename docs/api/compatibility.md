# API and protocol compatibility

`/v1` remains the API namespace. Successful existing response shapes remain readable; `requestId` is additive. Error responses consistently use `{ error: { code, message, requestId, details? } }`; internals are never returned for 5xx errors.

`POST /v1/intents` remains available for legacy unsigned v1 evidence and is deprecated. New clients use `POST /v1/authorizations/prepare` to create `priorseal.authorization.v2`, sign the returned EIP-712 typed data, submit it to `POST /v1/authorizations`, and pass `authorizationId` to `POST /v1/executions/observe`. This produces `priorseal.execution-receipt.v3`. V3 preserves the complete v2 authorization evidence and adds a signed `executionStatus` plus `priorseal.compliance-assessment.v1`. The observation response must return the requested transaction hash and chain. A confirmed or reverted transaction correlated by chain, delegated executor and nonce is assessable and consumes the single use: complete material agreement is `COMPLIANT`, while a material transfer or exact-call mismatch is `NON_COMPLIANT`. The additive `executionCorrelation` response field reports the complete action result as `MATCH`, `MISMATCH`, or `INDETERMINATE`; a mismatch does not reopen permission. Pending, unavailable, reorged and unrelated observations are `NOT_ASSESSABLE`. RFC 3161 deployments add `priorseal.rfc3161-evidence.v1`; witness-quorum deployments add `priorseal.witness-evidence.v1`. Verifiers must enforce the corresponding evidence whenever the signed policy contains `timestampPolicy` or `witnessQuorum`. Authorization v1 and receipt v1/v2 remain verification-compatible but are no longer issued by default. Each receipt generation has its own domain and identity calculation.

`priorseal.intent.v1` keeps transfer-semantic binding. `priorseal.intent.v2` supports two profiles. `priorseal.execution-profile.exact-call.v1` requires `action: "CONTRACT_CALL"` and explicit `nonce`, `callTarget`, `calldataHash`, and `transactionValue`; it is intended for router/swap and other multi-transfer calls. It binds the exact transaction envelope and deliberately does not infer recipient, asset, amount, or transfer uniqueness from emitted `Transfer` logs. `priorseal.execution-profile.erc4337-user-operation.v1` requires action `ERC4337_USER_OPERATION`, the smart-account nonce, an allowlisted EntryPoint chain/version/address/runtime-code hash, canonical UserOperation hash, and at least one context commitment. `/v1/executions/observe` checks deployed EntryPoint code at the inclusion block and the matching EntryPoint event. Its optional `safe-4337.v1` account-call profile decodes only a single Safe4337Module `CALL` from the outer `handleOps` calldata, binds target/value/inner-calldata hash, and uses transaction prestate tracing plus explicit runtime trust pins to verify the Safe proxy and singleton, module, module EntryPoint, enabled state, and fallback-handler slot at execution time. RPC providers without prestate tracing cannot serve this profile. Other account formats and batch/delegate calls are not semantically interpreted. Older intent and receipt schemas remain unchanged and verifiable.

New exact-call authorizations fail closed with `POLICY_EXACT_CALL_SEMANTICS_UNSUPPORTED` when the active policy configures `allowedAssets`, `allowedRecipients`, or `maxAmount`. Those fields cannot constrain the business semantics hidden inside arbitrary calldata. Use exact envelope constraints plus a namespaced context commitment and an independent composition verifier for partner-specific quote, risk, approval, or decision semantics. This does not change existing receipt verification or import a partner's policy meaning into PriorSeal.

New intent issuance accepts a single `chainId`; the unused legacy `chainIds` input is rejected. `constraints.minConfirmations` must be a JSON number. Historical signed artifacts continue to be verified according to their original schemas and bytes.

New intents may opt into `constraints.finalityRequirement: "RPC_FINALIZED"` and a numeric `constraints.maxToleratedReorgDepth` (0–9999). These fields are part of the signed intent hash; they do not alter historical signed bytes. The default `CONFIRMATIONS` criterion and legacy `finalityState: "CONFIRMED"` mean that the configured confirmation floor was met, not that the consensus protocol finalized the block. For the opt-in criterion, an included transaction's signed observation carries `priorseal.temporal-evidence.v1` with the effective confirmation floor, observed head height/hash, and RPC finalized block height/hash. A final `CONFIRMED` or `REVERTED` observation requires `finalityState: "FINALIZED"` and internally consistent temporal evidence. `priorseal-sdk@0.8.0` rejects the new signed intent constraint; upgrade external verifiers to 0.9.0 before opting in. The offline verifier replays arithmetic and signed policy checks but does not independently prove an RPC's canonical or finalized assertion. See [Temporal evidence and finality](../architecture/temporal-finality.md).

New intent and authorization issuance requires an explicit transaction `nonce` and requires `delegate.executor` to equal `intent.sender`, because the observed EVM transaction has one sender that must satisfy both bindings. Historical receipts remain verification-compatible. Authorization preparation evaluates the active principal and intent policy before returning wallet-signable EIP-712 data; acceptance evaluates it again against the current policy and acceptance time.

ERC-1271 organization authorization remains chain-state dependent. The server verifies `eth_chainId` on each configured endpoint before trusting `isValidSignature`; wrong-chain or unavailable endpoints produce `AUTHORIZATION_VERIFIER_UNAVAILABLE`, while a completed same-chain call returning a non-magic value produces `INVALID_AUTHORIZATION_SIGNATURE`.

Historical EVM anchors over a hash-chain head retain their v1 evidence shape and remain verifiable. New anchors commit to a Merkle root and use v2 transparency checkpoints with a compact inclusion proof; verifiers must branch on the signed checkpoint schema rather than interpreting one format as the other. New issuance and current verifiers require the anchor RPC to report the declared chain, require the configured confirmation floor, and reject an anchor whose block timestamp is later than the observed execution block. An incorrectly post-execution anchor is not accepted as pre-execution evidence.

Roll out this protocol change by publishing and deploying the updated offline SDK/verifiers before switching the issuer to v2 checkpoint issuance. Older SDK builds understand only v1 transparency evidence and correctly reject v2 receipts rather than silently skipping their proof. Migration 010 must be applied before the issuer is upgraded; it backfills the Merkle index in the same transaction as the migration record.

Standalone witnesses expose `POST /v1/witness/attest`, public liveness/readiness endpoints, and `GET /.well-known/priorseal-witness-key.json`. A successful attestation response is idempotent for the canonical request hash. Clients must trust the witness public key from the principal-signed authorization policy, not a key learned only from the same HTTP response.

`Idempotency-Key` is optional for compatibility and strongly recommended for writes. Reuse with the same request body returns the original result; reuse with different content returns `IDEMPOTENCY_CONFLICT`. Records expire after 24 hours.

OpenAPI is published at `/openapi/v1.json`. The source of truth for the signature protocol is the golden-vector and authorization tests plus canonical JSON. Do not reorder, omit, or normalize signed JSON fields. V1 and v2 receipts remain accepted; v3 receipt IDs additionally bind the receipt schema so historical and current statements for the same authorization and execution cannot collide.
