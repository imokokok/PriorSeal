# Operations runbook

Start locally: `cp .env.example .env.local`, configure only development RPC/key file paths, then run `npm ci`, `npm run start:api`, and `npm --prefix web run dev`. Use `GET /health/live` for process liveness and `/health/ready` for dependency readiness.

`GET /v1/capabilities` supplies public deployment profiles, audience, configured chain dependencies and proof mode. It does not expose principal allowlists or credentials, and does not probe RPC/TSA reachability. Check the selected chain's readiness as well as the aggregate workflow flag; authorization preparation remains the authoritative request-specific policy gate. The optional archive requires migration 009 and [project archive configuration](project-evidence-archive.md).

Before enabling signed authorization in a persistent environment, apply migrations through `010_authorization_merkle_index.sql`, set a deployment-specific `PRIORSEAL_AUTHORIZATION_AUDIENCE`, and place the strict JSON authorization policy at `PRIORSEAL_POLICY_FILE`. Policy allowlists must be JSON arrays; malformed allowlists fail startup instead of disabling the corresponding restriction. Changing either audience or policy intentionally invalidates authorizations prepared for the previous deployment policy. Keep the policy file under change control and retain each published policy hash with audit evidence. When named identity matters, include entries such as `{ "id": "acme-treasury", "type": "organization", "account": "0x...", "authorizerType": "eip1271" }` in `policy.principals` only after the identity-to-account relationship has been reviewed through your onboarding process.

For agents whose transaction key must not also grant principal authority, set `requireDistinctAuthorizerAndExecutor: true`. This rejects an authorization when `authorizer.address` equals `delegate.executor`, and the result is preserved in the signed policy evidence. Use a user wallet, Safe/ERC-1271 account or other reviewed authority for the principal side and a separate constrained executor for transaction signing. The policy proves which distinct accounts occupied the roles; key storage, process isolation and recovery controls still require an integrator-owned custody design.

Use either each `*_FILE` setting or its supported inline `*_JSON`/`*_PEM` counterpart, never both. Node and Cloudflare parse the same normalized policy and dependency documents. Production readiness checks every configured RPC endpoint's reported chain ID, and live ERC-1271 verification repeats that check before reading organization contract state. Treat `AUTHORIZATION_VERIFIER_UNAVAILABLE` as a retryable infrastructure failure; do not ask the organization to replace its signature unless the service returns `INVALID_AUTHORIZATION_SIGNATURE` from a completed same-chain check.

Do not apply `allowedAssets`, `allowedRecipients`, or `maxAmount` to exact-call intents: those are descriptive fields and cannot constrain arbitrary calldata semantics. PriorSeal rejects new exact-call authorizations under such a policy. Bind partner-owned business semantics with a namespaced context commitment and verify them in the composition layer while PriorSeal continues to bind only the exact transaction envelope.

Set `PRIORSEAL_ENVIRONMENT=production`, an immutable `PRIORSEAL_BUILD_VERSION`, a deployment-specific `PRIORSEAL_KEY_ID`, and explicitly choose `PRIORSEAL_PREEXECUTION_PROOF_MODE=rfc3161`, `witness-quorum`, or `evm-anchor`. Production startup fails unless the runtime has durable storage, issuer keys, a non-default issuer and audience, a non-localhost CORS origin, an explicit policy, and all dependencies for the selected proof mode. The Node runtime additionally requires both PostgreSQL URLs; the Worker runtime derives its immutable build version from Version Metadata and requires D1, Queue, and Rate Limiting bindings. Private deployments should keep `PRIORSEAL_ALLOW_SELF_ASSERTED_PRINCIPALS=false` and configure at least one reviewed principal. A public beta may explicitly set it to `true` and use `config/authorization-policy.public-beta.json`; in that mode wallet control is verified but the human-readable principal ID remains self-asserted.

For the simplest no-Gas mode, include `{ "schema": "priorseal.timestamp-policy.v1", "profile": "digicert-rfc3161-v1", "maxClockSkewSeconds": 300 }` as `timestampPolicy`. No additional credential is required. PriorSeal submits only the authorization hash to DigiCert's [documented RFC 3161 endpoint](https://knowledge.digicert.com/general-information/rfc3161-compliant-time-stamp-authority-server) at `http://timestamp.digicert.com`; integrity and authenticity come from strict verification of the signed RFC 3161 response, not transport security. Treat TSA unavailability as fail-closed: an authorization is not accepted without a verified token. Monitor availability and pin changes through a reviewed software release rather than dynamically trusting response certificates.

For the Gas-free mode, add `witnessQuorum` to the signed policy with a threshold of at least two and a distinct Ed25519 public key for each operator. Keep the corresponding HTTPS URLs and bearer tokens in the secret-mounted `PRIORSEAL_WITNESS_ENDPOINTS_FILE`. Deploy each witness under a separate operator/account, give it its own database and key pair, apply migration 005 to that database, and start it with `npm run start:witness`. Confirm `/health/ready` and `/.well-known/priorseal-witness-key.json`, then compare the published key to the signed policy out of band. A policy/key change requires new user authorizations because it changes `policyHash`.

Run `npm run production:check` against the migration environment before a release. It performs non-mutating checks for the production configuration, immutable build version, issuer private-key permissions, reviewed principals, migration 010 and its Merkle index, the durable observation-result and lease columns, evidence tables, RPC chain identities, and the selected proof-mode dependencies. `npm run release:check` also builds and validates the Cloudflare Worker bundle. A failed check blocks release. Follow the [Cloudflare runbook](cloudflare.md) for deployment and post-deploy verification.

The built-in authorization log is an issuer-signed, append-only hash chain. RFC 3161 mode adds an independent authority's signed time without a chain transaction; witness-quorum mode adds independently operated signatures. If EVM consensus is required instead, periodically anchor a signed checkpoint outside PriorSeal and provide the verified anchor record through `PRIORSEAL_TRANSPARENCY_ANCHOR_FILE`. Production EVM-anchor mode requires that source at startup. The runtime verifies its declared chain, canonical transaction and block plus `PRIORSEAL_ANCHOR_CONFIRMATIONS` (default `12`). Execution fails before consuming the authorization unless the anchor covers it and its block timestamp is no later than the execution block timestamp. The reference `PriorSealTransparencyAnchor.sol` contract is unaudited; deploy it only after review, make its owner a reviewed multisig, and wait for the required finality.

After an audited anchor contract is deployed and migration 010 is applied, set `PRIORSEAL_ANCHOR_CHAIN_ID` and `PRIORSEAL_ANCHOR_CONTRACT`. Run `npm run anchor:prepare` with a direct database URL to produce public transaction calldata for the latest Merkle root, submit that call from the external owner multisig, then set `PRIORSEAL_ANCHOR_TX_HASH` and run `npm run anchor:record`. The record command requires the configured confirmation threshold, checks chain ID, target, successful receipt, calldata, block and timestamp, and matches the on-chain commitment to the local Merkle root or a historical hash-chain head. It writes the public anchor record without handling a wallet private key. Restart or roll the service after updating the record, then call the authorization transparency endpoint before permitting the agent to execute.

When RPC failures rise, do not mark transactions failed. Check endpoint health/chain ID, rotate to a configured fallback, and replay affected jobs. For a reorg, retain the original receipt, re-observe after finality, issue a new receipt marked `REORGED`/superseding evidence, and notify relying systems.

For issuer-key rotation: place historical public keys in a public-only JSON file and set `PRIORSEAL_KEY_REGISTRY_FILE` to its path. The file shape is `{ "schema": "priorseal.keys.v1", "keys": [{ "issuer": "priorseal", "keyId": "old", "algorithm": "Ed25519", "publicKey": "-----BEGIN PUBLIC KEY-----...", "status": "retired", "validFrom": 1700000000, "validUntil": 1800000000 }] }`. Configure the new signing key under a new `PRIORSEAL_KEY_ID`; the active key is merged into the published registry. Never put private-key fields in this file. Before a planned rotation, complete or reissue outstanding accepted authorizations because an execution receipt and its embedded acceptance currently require the same issuer key. After rotation, an old-key authorization fails closed without being consumed or persisting an invalid receipt. If an issuer key is compromised, mark it revoked, rotate immediately, preserve audit evidence, and disclose affected receipt time ranges.

For legacy RPC URL exposure: releases before the source-identifier fix could embed the entire configured endpoint in observations and signed receipts. Do not rewrite signed receipts because doing so invalidates their signatures. Immediately rotate any RPC credential embedded in a URL, update `PRIORSEAL_RPC_*`, restart the service, and stop distributing old receipt files until the credential is invalid. Unsigned observation rows may be access-restricted or removed only under the organization's evidence-retention policy.
