# ERC-4337 UserOperation authorization

PriorSeal's ERC-4337 SDK adapter binds one canonical UserOperation hash into a normal PriorSeal authorization intent and verifies its matching EntryPoint `UserOperationEvent` in a transaction receipt. It supports EntryPoint versions 0.6 through 0.9 using viem's canonical hash implementation.

## EIP-7702 with EntryPoint v0.8/v0.9

PriorSeal supports the EIP-7702 EOA path with EntryPoint v0.8 or v0.9. This is separate from the Safe profile above: use an EOA as the UserOperation sender, and pin the exact delegate implementation that the EOA will execute. The SDK binds the canonical UserOperation hash, delegate address, delegate runtime-code hash, and—when the operation carries a signed authorization—the complete authorization tuple. The tuple commitment is a PriorSeal commitment to `(chainId, address, nonce, yParity, r, s)`; it is not the EIP-7702 signing digest.

The operator must add independently reviewed deployment pins before authorizations can be observed. Configure both the EntryPoint and delegate for each supported chain; never use a wildcard or a hash copied from an unrelated deployment:

```dotenv
PRIORSEAL_ERC4337_ENTRY_POINTS_JSON='[{"chainId":8453,"version":"0.8","address":"<verified-entrypoint-address>","codeHash":"<verified-entrypoint-runtime-code-hash>"}]'
PRIORSEAL_EIP7702_DELEGATE_TRUST_JSON='[{"chainId":8453,"address":"<audited-delegate-address>","codeHash":"<audited-delegate-runtime-code-hash>"}]'
```

Use values read from the same chain and checked against the release or audit artifact. The delegate must have deployed runtime code, and the service checks its hash against both the operator's allowlist and the transaction trace. The RPC endpoint must support Geth-compatible `debug_traceTransaction` with `prestateTracer` and diff mode. Without those transaction-level states PriorSeal fails closed; ordinary block-end `eth_getCode` is not enough to claim whether the delegation survived a reverted transaction.

Build the intent from the exact operation returned by the wallet or bundler. Include the signed authorization only when this UserOperation is requesting a fresh delegation; an already delegated EOA can omit it. In both cases `factory: '0x7702'` is required by the EIP-7702 EntryPoint format, and the SDK binds the trusted delegate:

```ts
import {
  bindERC4337UserOperation,
  buildERC4337UserOperationIntent,
} from 'priorseal-sdk'

const operationInput = {
  chainId: 8453,
  entryPoint: verifiedEntryPointAddress,
  entryPointCodeHash: verifiedEntryPointCodeHash,
  entryPointVersion: '0.8' as const,
  userOperation: {
    ...walletUserOperation,
    factory: '0x7702',
    // Include the actual signed EIP-7702 tuple when authorizing now.
    // authorization: { address, chainId, nonce, yParity, r, s },
  },
  eip7702: {
    delegateAddress: auditedDelegateAddress,
    delegateCodeHash: auditedDelegateRuntimeCodeHash,
  },
}

const binding = bindERC4337UserOperation(operationInput)
const intent = buildERC4337UserOperationIntent({
  ...operationInput,
  intentId: `7702-${binding.userOpHash.slice(2, 14)}`,
  validUntil,
})
```

The SDK accepts viem's `authorization` property and the ERC-4337 RPC spelling `eip7702Auth`, and normalizes either before hashing. Continue through the ordinary PriorSeal prepare, wallet-sign, accept and observe flow. The outer transaction hash comes from the bundler receipt. At observation time PriorSeal checks the configured EntryPoint code, reconstructs the exact v0.8/v0.9 `handleOps` UserOperation and recomputes its hash, recovers the authority from the type-4 transaction's authorization list, matches the signed tuple, verifies the matching `UserOperationEvent` when the outer transaction succeeds, and checks the sender's delegated code plus transaction-end state. Do not treat the bundler's returned UserOperation hash alone as inclusion evidence.

Failure and recovery evidence distinguish two cases:

- If `handleOps` succeeds but the UserOperation fails, the matching event supplies `success=false` and operation-level gas. This is a final failed operation; it may still have consumed gas.
- If the outer transaction reverts, the event and operation-level result are absent. PriorSeal can still establish that the exact operation hash and authorization tuple were in the reverted transaction calldata, records the outer transaction's gas/fee, and traces whether the EIP-7702 delegation is active after the revert. It reports `operationSuccess: null`; it never turns calldata presence into a claim that the UserOperation executed. The authorization can be correlated as a final failure/recovery record only when the configured delegate is observed active at transaction end. If that state is absent or different, the observation does not match the authorized delegation.

This profile currently accepts `handleOps` bundles for EntryPoint v0.8/v0.9. It does not decode `handleAggregatedOps`, custom bundler transaction methods, Safe account calls, or other smart-account implementations. The observer requires the transaction trace and fails closed if the provider omits the sender/delegate state or returns malformed traces. A delegate code pin should refer to code with an independent security review; matching a hash proves identity, not that the implementation is safe.

## MetaMask EIP-7702 on Base Sepolia

The Base Sepolia MetaMask `EIP7702StatelessDeleGatorImpl` at `0x63c0c19a282a1B52b07dD5a65b58948A07DAE32B` is bound by its `entryPoint()` getter to EntryPoint v0.7 at `0x0000000071727De22E5E9d8BAf0edAc6f37da032`. It cannot be used through EntryPoint v0.8 at `0x4337084D9E255Ff0702461CF8895CE9E3b5Ff108`. The deployment source is [MetaMask's Base Sepolia contract verification](https://sepolia.basescan.org/address/0x63c0c19a282a1b52b07dd5a65b58948a07dae32b), and the canonical v0.8 address is listed in the [ERC-4337 v0.8 release](https://github.com/eth-infinitism/account-abstraction/releases).

PriorSeal now supports the predelegated v0.7 observation profile for this delegate. MetaMask's [EOA-upgrade tutorial](https://docs.metamask.io/tutorials/upgrade-eoa-to-smart-account/) uses EIP-5792 to upgrade an EOA and send an atomic batch; the tutorial does not specify that the resulting transaction is an EntryPoint `handleOps` bundle. Treat the wallet method result as a submission/status signal only. PriorSeal evidence is available only when the observed transaction targets the pinned v0.7 EntryPoint and contains the exact UserOperation. The SDK binds its hash, delegate address and runtime-code hash; the observer reconstructs the v0.7 `handleOps` operation, checks the delegate's on-chain `entryPoint()` against the selected EntryPoint, and traces execution through the pinned delegate.

This v0.7 profile observes an already delegated EOA only. It does not support adding a fresh EIP-7702 authorization in the same v0.7 UserOperation. Fresh authorization tuples remain supported by the separate v0.8/v0.9 marker-based profile above. MetaMask's current [Smart Accounts Kit EIP-7702 quickstart](https://docs.metamask.io/smart-accounts-kit/get-started/smart-account-quickstart/eip7702/) is for embedded wallets and notes `signAuthorization` does not support JSON-RPC accounts; it does not document a configurable EntryPoint version for the MetaMask Connect EOA flow. Confirm the wallet's actual UserOperation signing and bundler path before a live run; a `wallet_sendCalls` result alone is not a v0.7 `handleOps` inclusion.

`npm run erc4337:eip7702:doctor` performs read-only Base Sepolia checks for EntryPoint v0.7, the MetaMask delegate's `entryPoint()` getter and runtime-code hash, RPC `prestateTracer`, and bundler support. It never connects to MetaMask, signs, or submits. A green infrastructure result does not check a particular wallet's delegation state, balance, or exact operation fee. Do not submit the MetaMask v0.7 delegate through the v0.8 EntryPoint.

The development console includes a dedicated MetaMask testnet route at `/app/eip7702-pilot`; start it with the same local API and UI commands listed in the Safe pilot section. This route is for a Base Sepolia EOA and requires the API to advertise the ERC-4337 EIP-712 profile. It first checks `wallet_getCapabilities` for atomic EIP-5792 `wallet_sendCalls` support. If the EOA is not delegated, it asks MetaMask to prepare a separate two-call, zero-value setup batch, saves the batch ID in tab session storage, and verifies `wallet_getCallsStatus` plus the account's on-chain delegation before continuing. The wallet batch result is only a setup status; it is never treated as a PriorSeal-authorized UserOperation or an EntryPoint inclusion.

For an already delegated EOA, the page checks the delegate designator, the delegate runtime-code hash, its `entryPoint()` getter, the EntryPoint runtime-code hash, the bundler chain and its supported EntryPoints. It estimates a single zero-value empty `execute` call, checks the EOA balance plus EntryPoint deposit against the conservative maximum fee, and then asks MetaMask to sign the packed v0.7 UserOperation. Before accepting that signature, the adapter compares its EIP-712 digest with `getPackedUserOperationTypedDataHash` on the delegated account and recovers the signer to the connected EOA. PriorSeal then authorizes the exact UserOperation hash and delegate pins. Submission is a later user-confirmed step.

The route stores a validated recovery checkpoint in `sessionStorage` before a bundler request. Recovery checks the bundler receipt, bundler hash lookup and a narrowly filtered EntryPoint event, then asks PriorSeal for finality and trace-backed delegate evidence. It never resubmits automatically. A one-time retry after an uncertain submission requires all three lookups to succeed with no result, an unchanged EntryPoint nonce, an active pinned delegate, a fresh PriorSeal authorization for the same signed operation and a second explicit submission review. Export is enabled only after final evidence matches the saved hash and authorization; it includes the operation, delegate and EntryPoint pins, authorization, observation, receipt and observation job. A final operation revert is preserved as a failure outcome with gas evidence.

This pilot is intentionally limited to MetaMask's Base Sepolia `EIP7702StatelessDeleGatorImpl` with an already delegated EOA and EntryPoint v0.7. It does not add an authorization tuple to a v0.7 UserOperation, and it does not treat an EIP-5792 setup batch as an ERC-4337 execution. The local RPC proxy keeps RPC and bundler endpoints server-side and only forwards its allowlisted pilot methods. Do not expose provider URLs in client configuration or use a real-value call in this test route.

To open the local wallet pilot, start `npm run erc4337:pilot:api` and `npm run erc4337:pilot:ui` in separate terminals from the repository root, then open `http://127.0.0.1:8765/app/erc4337-pilot` in Chrome with MetaMask. The UI server keeps the SolidRPC and bundler URLs server-side and proxies only the required JSON-RPC methods. The pilot prepares a single zero-value Safe `CALL` to the owner EOA; signing the Safe operation and PriorSeal authorization are separate wallet reviews, and bundler submission is a third explicit review. No wallet action is triggered by opening or estimating the page.

After authorization, the pilot keeps the signed UserOperation, its expected hash, the PriorSeal authorization ID, submission-attempt count, and any outer transaction hash in this browser tab's `sessionStorage`. It stores a `SUBMITTING` checkpoint before the first bundler request and changes it to `SUBMITTED` only after the bundler returns the exact expected hash. A timeout or mismatched response therefore remains an uncertain submission; recovery never resubmits automatically.

Recovery gives the bundler receipt, bundler hash lookup, and a narrowly filtered UserOperationEvent lookup independent 18-second deadlines. A positive inclusion from any source proceeds to PriorSeal observation. A negative result is considered complete only when all three lookups succeed; provider failure, ambiguity, or a UserOperation still known to the bundler keeps the operation in read-only recovery. Only after all three return no result does the pilot check the Safe call, signature validity window, on-chain nonce, balance, and maximum fee. A manual retry requires a fresh PriorSeal authorization and a second explicit submission confirmation, is limited to one retry, and reuses the exact saved hash. This cannot prove that another bundler or provider does not still hold the operation, so a competing inclusion can still waste test gas.

The pilot authorization binds at least two confirmations and a one-block reorg buffer, and preserves any stronger deployment requirement, including `RPC_FINALIZED`. `PENDING` and `REORGED` observations never become complete or exportable. A reorg clears the saved outer transaction hash and returns recovery to read-only UserOperation/event lookup. Final export requires a matching Safe, EntryPoint, UserOperation hash, nonce, decoded call, finality evidence, authorization correlation, and verified receipt when a receipt is configured. A reverted UserOperation is a terminal, exportable failure record: the EntryPoint event records `success=false` and actual gas charged even if the outer bundle transaction succeeded.

The checkpoint contains no private key and closing the tab discards it. It is validated against the pinned EntryPoint and recomputed UserOperation hash before recovery. Download the pilot evidence bundle before leaving the page; it contains the signed operation, accepted authorization and acceptance, final observation, receipt when configured, and observation job when present. Downloading clears the tab checkpoint. The signed operation is authorization evidence; protect and retain the exported file as an execution artifact.

```ts
import {
  bindERC4337UserOperation,
  buildERC4337UserOperationIntent,
  computeERC4337EntryPointCodeHash,
  verifyERC4337ExecutionEvidence,
} from 'priorseal-sdk'
import { buildInsightPriorSealContextCommitment } from 'oracle-insight-guard'

const trustedEntryPointCodeHash = '0x8db5ff695839d655407cc8490bb7a5d82337a86a6b39c3f0258aa6c3b582fc58' as `0x${string}`
const operationInput = {
  chainId: 84532,
  entryPoint: '0x0000000071727De22E5E9d8BAf0edAc6f37da032', // EntryPoint v0.7 on Base Sepolia.
  entryPointCodeHash: trustedEntryPointCodeHash, // Compare the live code hash to this independently verified pin first.
  entryPointVersion: '0.7' as const,
  accountCallProfile: 'safe-4337.v1' as const, // Optional; enables Safe single-call semantic binding.
  userOperation, // Full operation returned by the wallet or bundler, before submission.
}

const observedEntryPointCodeHash = computeERC4337EntryPointCodeHash(
  await publicClient.getCode({ address: operationInput.entryPoint }),
)
if (observedEntryPointCodeHash !== trustedEntryPointCodeHash) throw new Error('Unexpected Base Sepolia EntryPoint code')

const binding = bindERC4337UserOperation(operationInput)
// Build this from the two signed Insight pre-trade attestations after your
// normal Insight verification and trust checks have passed.
const insightCommitment = buildInsightPriorSealContextCommitment({
  sourceAttestation,
  destinationAttestation,
  maxSlippageBps: 50,
})
const intent = buildERC4337UserOperationIntent({
  ...operationInput,
  intentId: `withdrawal-${binding.userOpHash.slice(2, 14)}`,
  validUntil,
  contextCommitments: [insightCommitment],
})

// Submit `intent` through the existing PriorSeal prepare/sign/accept flow;
// retain the verified/accepted authorization returned by that flow.
const acceptedAuthorization = await priorseal.acceptAuthorization(/* signed authorization */)
// After the bundler includes the operation, observe the outer transaction hash.
// PriorSeal uses the accepted intent's UserOperation binding to inspect it.
const result = await priorseal.observeExecution({
  authorizationId: acceptedAuthorization.authorization.authorizationId,
  chainId: operationInput.chainId,
  txHash: bundlerTransactionHash,
})

// Verify the PriorSeal signature/trust first; then cross-check its signed
// execution object against the original UserOperation and authorization.
if (!result.receipt || result.verification?.valid !== true) throw new Error('PriorSeal receipt verification failed')
const executionEvidence = verifyERC4337ExecutionEvidence({
  binding,
  intent: acceptedAuthorization.authorization.intent,
  receipt: result.receipt.execution,
})
```

`buildERC4337UserOperationIntent` sets the intent sender to the smart-account address and includes the canonical operation hash as the `priorseal.erc4337.user-operation.v1` commitment. Insight's existing `buildInsightPriorSealContextCommitment` can bind the source/destination pre-trade pair into the same signed authorization. Applications can use the existing authorization flow with a smart-account `principal.account`; smart accounts that authorize contract signatures use the existing EIP-1271 route. The commitment links the attestations but does not verify their signatures or trust: perform Insight's normal signature, key, policy and freshness checks before relying on the risk decision.

The server observer checks the configured EntryPoint address and runtime bytecode hash at the UserOperation's inclusion block, then checks the event signature, operation hash, account sender, nonce, success flag and gas fields. When `accountCallProfile: 'safe-4337.v1'` is selected, it also decodes the actual EntryPoint `handleOps` transaction, finds the operation matching the event sender and nonce, and decodes Safe's `executeUserOp` or `executeUserOpWithErrorString`. The profile binds one `CALL` target, native value and inner calldata hash; it rejects `DELEGATECALL`, batches and unsupported bundler transaction methods. It requires `debug_traceTransaction` with Geth's `prestateTracer` (and fails closed if the RPC does not provide it), so the trust checks use state immediately before this transaction rather than block-end state. It checks the Safe proxy runtime-code hash, reads its singleton from storage slot 0 and checks the singleton code hash, checks the Safe4337Module code hash, verifies the module mapping is enabled and the Safe fallback-handler slot points to that module. The trust entry pins the module to the intended EntryPoint; operators must verify that the pinned module deployment's immutable `SUPPORTED_ENTRYPOINT()` matches that address. These checks follow the [Safe proxy storage layout](https://github.com/safe-fndn/safe-smart-account/blob/main/contracts/libraries/SafeStorage.sol), [Safe fallback manager](https://github.com/safe-fndn/safe-smart-account/blob/main/contracts/base/FallbackManager.sol), and [Safe4337Module](https://github.com/safe-fndn/safe-modules/blob/main/modules/4337/contracts/Safe4337Module.sol). This decoding establishes what the calldata encodes, not the downstream contract's economic effect.

The observer applies the existing block canonicality/finality checks and includes the decoded call in the signed PriorSeal receipt. Configure `PRIORSEAL_ERC4337_ENTRY_POINTS_JSON` with the verified Base Sepolia entry `[{"chainId":84532,"version":"0.7","address":"0x0000000071727De22E5E9d8BAf0edAc6f37da032","codeHash":"0x8db5ff695839d655407cc8490bb7a5d82337a86a6b39c3f0258aa6c3b582fc58"}]`. Safe semantic observation additionally needs `PRIORSEAL_SAFE_4337_TRUST_JSON`, for example `[{"chainId":84532,"version":"0.7","entryPointAddress":"0x0000000071727De22E5E9d8BAf0edAc6f37da032","moduleAddress":"0x75cf11467937ce3F2f357CE24ffc3DBF8fD5c226","moduleCodeHash":"0x2aea997c4e3cf0e2f333025372e219abcfde81c21fc2f8fb066414a5685dd3e0","safeProxyCodeHash":"0xd7d408ebcd99b2b70be43e20253d6d92a8ea8fab29bd3be7f55b10032331fb4c","safeSingletonCodeHash":"0xb1f926978a0f44a2c0ec8fe822418ae969bd8c3f18d61e5103100339894f81ff"}]`. These trust entries are explicit per-chain/version pins; PriorSeal does not guess addresses or hashes. The EntryPoint, module, Safe proxy and singleton hashes above were read from Base Sepolia; independently verify them against the RPC endpoint used by the service. Also confirm the pinned module's immutable supported EntryPoint matches `entryPointAddress`. Safe semantic observation requires an RPC endpoint with transaction prestate tracing; ordinary receipt and block RPC support is not enough. Observation fails closed if tracing is unavailable or the configured on-chain code, EntryPoint, module enablement, or fallback handler differs at execution time. The raw-receipt mode of `verifyERC4337ExecutionEvidence` cannot fetch deployed bytecode or decode the outer transaction; use the signed PriorSeal observation for the Safe call profile. The flow does not prove token balance changes or establish business-policy compliance. A failed UserOperation may still consume gas even when the bundler transaction succeeds.

The account decoder currently supports only the documented Safe4337Module single-call form. Safe batches, delegate calls, other Smart Account implementations, `handleAggregatedOps`, and custom bundler entry methods fail closed when this profile is selected. Without the profile, PriorSeal still binds the full UserOperation hash and makes no account-call semantic claim.
