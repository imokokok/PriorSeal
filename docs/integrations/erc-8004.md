# ERC-8004 agent identity and accountability

PriorSeal can bind an ERC-8004 agent reference to its existing signed `delegate.agentId`, resolve the agent's on-chain `agentWallet`, and commit a block-pinned identity snapshot to supported PriorSeal intent profiles. It can also read reputation and validation records through caller-allowlisted registries, evaluate buyer-defined trust policies, and submit feedback or validation requests only through an explicitly supplied wallet client.

ERC-8004 is currently a draft. Treat its registries as versioned adapters configured by each deployment. The registry address, chain, validator/reviewer set, and interpretation policy remain explicit trust inputs. PriorSeal does not issue a universal agent score.

## Identity binding

Use the complete identity reference, including chain, identity-registry contract, and token ID. Do not use a bare display name or token ID as a global identity.

```ts
import {
  buildExactCallIntent,
  createPriorSealClient,
  erc8004IdentitySnapshotCommitment,
  formatERC8004AgentRef,
  resolveERC8004Identity,
  verifyERC8004AuthorizationBinding,
} from 'priorseal-sdk'

const agentRef = formatERC8004AgentRef({
  chainId: 84532,
  identityRegistry: '0x1111111111111111111111111111111111111111',
  agentId: '42',
})

const snapshot = await resolveERC8004Identity(publicClient, agentRef, {
  trustedRegistryAddresses: ['0x1111111111111111111111111111111111111111'],
  // Pin known runtime code hashes in production deployments where practical.
  trustedRegistryCodeHashes: ['0x2222222222222222222222222222222222222222222222222222222222222222'],
  executor: '0x3333333333333333333333333333333333333333',
})
if (snapshot.bindingStatus !== 'MATCH') throw new Error('The registered agentWallet does not match the executor')

const identityCommitment = erc8004IdentitySnapshotCommitment(snapshot)
const intent = buildExactCallIntent({
  transaction: reviewedTransaction, // The application's reviewed exact EVM call.
  intentId: crypto.randomUUID(),
  asset: 'eip155:84532/erc20:0x6666666666666666666666666666666666666666',
  amount: '1',
  validUntil: Math.floor(Date.now() / 1000) + 300,
  contextCommitments: [identityCommitment],
})
const priorseal = createPriorSealClient({ baseUrl: 'https://priorseal.xyz' })
const flow = await priorseal.authorizeWithWallet({
  intent,
  principal: { type: 'user', id: 'user:42' },
  delegate: { agentId: agentRef, executor: snapshot.executor! },
}, window.ethereum)

const identityReview = await verifyERC8004AuthorizationBinding(
  flow.accepted.authorization,
  snapshot,
  publicClient,
  { trustedRegistryAddresses: ['0x1111111111111111111111111111111111111111'] },
)
if (!identityReview.valid) throw new Error(identityReview.code)
```

`resolveERC8004Identity` reads `ownerOf`, `getAgentWallet`, `tokenURI`, registry bytecode, and block metadata at one pinned block. A registry must be explicitly allowlisted. The `agentWallet` must be nonzero and match the executor. Registry code hashes can be pinned as an additional deployment policy.

The SDK never fetches `tokenURI`. Registration documents may use arbitrary URI schemes and are untrusted input; a caller that fetches one must apply its own network and content safety rules. Use `validateERC8004RegistrationFile` to check a document supplied by the caller and ensure it declares the same agent reference.

`verifyERC8004AuthorizationBinding` checks four separate relationships: the signed delegate ID, the executor-to-`agentWallet` match, the identity-snapshot context commitment, and the historical chain state at the snapshot block. It does not replace normal PriorSeal receipt/signature verification or establish trust in the RPC provider. Historical verification requires an RPC with state available at that block.

The existing v2 authorization signs `delegate.agentId` without changing its typed-data fields. Snapshot commitments use the existing context-commitment support in exact-call and ERC-4337 intent v2 profiles. Legacy transfer intents without context commitments can bind the canonical identity string, but cannot claim that a particular identity snapshot was signed; use a supported context-commitment profile when that relationship is required.

## Reputation signals

Read only from reviewers selected by the buyer's policy. The SDK reads each configured reviewer's indexed feedback, retains revocation state, caps history per reviewer, and records the snapshot block. Reputation feedback does not expose a creation timestamp through `readFeedback`; do not apply age claims to feedback entries based on this snapshot alone.

```ts
import { readERC8004Reputation, verifyAndEvaluateERC8004Reputation } from 'priorseal-sdk'

const reputationPolicy = {
  trustedReviewers: ['0x4444444444444444444444444444444444444444'],
  minimumFeedbackCount: 2,
  minimumDistinctReviewers: 1,
  requiredTag1: 'authorization-compliance',
}
const reputation = await readERC8004Reputation(publicClient, agentRef, reputationRegistry, reputationPolicy, {
  trustedRegistryAddresses: [reputationRegistry],
  maxFeedbackPerReviewer: 128,
})
const reputationDecision = await verifyAndEvaluateERC8004Reputation(
  publicClient,
  reputation,
  reputationPolicy,
  { trustedRegistryAddresses: [reputationRegistry] },
)
```

The evaluation's `result` remains `INDETERMINATE` until the SDK re-reads the registry at the recorded block and confirms the snapshot. `policyResult` reports the calculation over the supplied records; do not use it by itself as an authorization decision. Truncated reviewer histories also remain indeterminate. Reviewer addresses must come from the buyer's independently reviewed trust configuration.

## Validation signals

Read validation status only for explicitly named request hashes. The SDK checks that the validation registry points to the referenced identity registry, each request belongs to the expected agent, and each validator appears in the buyer's trusted-validator set before policy evaluation. A successful validation status proves only the validator's recorded response and the scope named by its request.

```ts
import { readERC8004Validations, verifyAndEvaluateERC8004Validations } from 'priorseal-sdk'

const validationPolicy = {
  trustedValidators: ['0x5555555555555555555555555555555555555555'],
  minimumResponse: 100,
  maxAgeSeconds: 86400,
}
const validations = await readERC8004Validations(
  publicClient,
  agentRef,
  validationRegistry,
  [requestHash],
  { trustedRegistryAddresses: [validationRegistry] },
)
const validationDecision = await verifyAndEvaluateERC8004Validations(
  publicClient,
  validations,
  validationPolicy,
  { trustedRegistryAddresses: [validationRegistry] },
)
```

## Sign the trust decision

When a buyer's authorization policy depends on ERC-8004 signals, create a trust-decision bundle before signing. The bundle includes the identity snapshot, the selected reputation/validation snapshots, the exact policy objects, and chain-verified evaluation results. Its context commitment binds that complete decision to the principal-signed intent.

```ts
import {
  buildExactCallIntent,
  createERC8004TrustDecisionBundle,
  verifyERC8004AuthorizationTrustDecision,
} from 'priorseal-sdk'

const trustedIdentityRegistries = [snapshot.identityRegistry]
const trustedReputationRegistries = [reputationRegistry]
const trustedValidationRegistries = [validationRegistry]
const bundle = await createERC8004TrustDecisionBundle(publicClient, {
  identitySnapshot: snapshot,
  reputation: { snapshot: reputation, policy: reputationPolicy },
  validations: { snapshot: validations, policy: validationPolicy },
  assessedAt: Math.floor(Date.now() / 1000),
}, {
  identityRegistry: { trustedRegistryAddresses: trustedIdentityRegistries },
  reputationRegistry: { trustedRegistryAddresses: trustedReputationRegistries },
  validationRegistry: { trustedRegistryAddresses: trustedValidationRegistries },
})

const intent = buildExactCallIntent({
  transaction: reviewedTransaction,
  intentId: crypto.randomUUID(),
  asset: reviewedAsset,
  amount: reviewedAmount,
  validUntil,
  contextCommitments: [bundle.commitment],
})
const flow = await priorseal.authorizeWithWallet({
  intent,
  principal: { type: 'organization', id: 'treasury:main' },
  delegate: { agentId: bundle.agentRef, executor: bundle.executor },
}, window.ethereum)

const trustReview = await verifyERC8004AuthorizationTrustDecision(
  flow.accepted.authorization,
  bundle,
  publicClient,
  {
    identityRegistry: { trustedRegistryAddresses: trustedIdentityRegistries },
    reputationRegistry: { trustedRegistryAddresses: trustedReputationRegistries },
    validationRegistry: { trustedRegistryAddresses: trustedValidationRegistries },
  },
)
```

`createERC8004TrustDecisionBundle` fails closed unless the identity is bound to its registered wallet and every included reputation or validation policy passes against chain-verified snapshots. Include one or both sources; when both are included, both must pass. `verifyERC8004AuthorizationTrustDecision` re-reads every source at its recorded block, recomputes the policy result and bundle digest, then matches that digest and agent/executor identity to the signed authorization. This establishes evidence binding and policy satisfaction; it does not establish that every application signer path enforced the policy at runtime. The caller should retain the bundle beside the PriorSeal receipt.

## Writing feedback and validation records

`submitERC8004Feedback`, `submitERC8004ValidationRequest`, and `submitERC8004ValidationResponse` send a transaction through the supplied viem `WalletClient`. They do not use or store a private key. Call them only after presenting the exact chain, registry, agent, content URI/hash, value, validator, and tags for the connected wallet to approve.

Feedback publication rejects the agent owner and approved operators, matching the ERC-8004 reputation rules. Validation-request publication checks owner/operator control. Validation responses require the connected wallet to match the validator address recorded for that request. The EVM registry remains authoritative and can reject a transaction if state changes between the preflight read and inclusion.

Use `hashERC8004Payload` for a canonical JSON keccak256 commitment within PriorSeal's integration profile. Use `hashERC8004ContentBytes` for an ERC-8004 `feedbackHash` or `requestHash` that must match exact content: it hashes a string as UTF-8 or a supplied `Uint8Array` byte-for-byte. Canonical JSON hashing is not a substitute for the file-byte hash. Keep personal or commercially sensitive receipt content off-chain; publish a content-addressed URI or digest only after explicit user consent. A PriorSeal receipt can support a narrowly scoped claim about authorization and observed execution, not a general claim about agent quality, economic outcome, or safety.

## Trust and deployment rules

- Configure identity, reputation, and validation registry allowlists separately for each chain and policy.
- Pin registry runtime code hashes where known; record the code hash and block in exported snapshots.
- Verify the PriorSeal receipt independently before evaluating the identity relationship.
- Keep RPC trust, registry trust, reviewer/validator trust, and PriorSeal issuer-key trust distinct.
- Preserve `PASS`, `FAIL`, and `INDETERMINATE` separately. Missing archive state or an unavailable RPC is not a pass.
- Treat reputation publication as an explicit wallet action; never submit feedback automatically after execution.
- Do not fetch arbitrary registration endpoints from a server. A future indexer needs SSRF controls, URI scheme restrictions, response size/time limits, and content-hash checks.
